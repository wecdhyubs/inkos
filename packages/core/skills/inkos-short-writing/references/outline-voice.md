# 大纲要说人话

大纲 / 提纲 / 单元计划 / chapter memo 是**写给执笔的人看的施工说明**，不是交给评审的汇报材料。它只需要说清「下一笔写什么」，不需要证明自己很专业。

InkOS 原版的章节 memo 要求填「即时动作、活跃读者期待、兑现或延迟、安静拍功能、人物选择因果、终态变化、钩子推进」。本包 1.0.0 把它泛化成「目的 / 进入状态 / 阻力 / 动作证据 / 转折 / 遗留」六要素表 —— 换了一批词，毛病一样：**把大纲写成了字段填空表，读完之后脑子里没有画面，仍然不知道要写哪一场戏**。1.1.0 起，改成先写人话。

## 先看对照

机器腔（真事一句没有）：

```text
| 单元 | 功能 | 活跃期待 | 阻力 | 终态变化 | 钩子推进 |
| 第 8 章 | 推进主线并深化人物关系 | H-03 待兑现 | 信息不对称 | 认知升级 | H-03 advance |
```

```text
本章通过多线叙事进一步强化主线的紧迫感，围绕核心冲突完成关键信息的递进式释放，
为后续反转埋下伏笔，实现读者契约的阶段性兑现。主线占比 60%，情感线占比 40%。
```

人话（一眼知道要写什么）：

```text
第 8 章｜林砚去档案室调三年前的巡检表，管理员说原件上周被借走了，
借条上签的是她师父的名字。她没声张，把借阅登记拍了下来。
这一章写完，她手里多了一张能证明师父撒谎的纸，也第一次不敢接师父的电话。
下一章得写她去找借走原件的人，或者干脆去问师父本人。
附注：H-03 推进；约 1800 字。
```

后者能直接动笔：地点、动作、物件、阻碍、变化、下一单元的理由都在。台账 ID 和字数还在，只是退到附注里。

## 硬规则

1. **一条大纲 = 一到三句具体事件**。主语是人、机构或一份具体材料，动词是看得见的动作，宾语是具体的东西。读完要能回答：谁在哪儿、想干什么、撞上什么、做了什么、结果多了/少了/知道了/失去了什么。
2. **先写人话，再补字段**。契约名、台账 ID、字数预算、口径、比例是机器层，放在事件句之后的附注或单独一格。**不许用字段表取代事件句**，也不许把大纲写成一列标签配一列空话。
3. **不写「功能 / 作用 / 意义」**。「推进主线」「深化主题」「强化张力」「完成信息释放」「实现阶段性兑现」「形成闭环」——这些是审稿词，不是施工说明。直接写发生了什么，功能读者自己看得出来。
4. **不解释、不预告、不自评**。删掉「本章旨在」「通过……从而……」「为后续埋下伏笔」「有效提升读者期待」「节奏紧凑」「有张力」。想埋伏笔，就把那件东西写出来：原件借条留在档案室，第 9 章去查借走它的人。
5. **计划别写成已完成**。用「要去 / 会发现 / 被拦下 / 将核对」或中性的现在时写待发生的事；别写「已查明」「成功说服」「终于意识到」，除非那是上一单元已经确立的事实。
6. **抽象名词换成具体**。赋能、抓手、维度、层面、闭环、系统性、整体上、进一步、相关方面、若干细节、一定程度、多维度、阶段性成果——每个都换成一个具体的人、动作、物件、数字或时间。写不出具体，说明这一单元还没想清楚，先别列进大纲。
7. **比例不进正文**。用户指定了各线比例，就用单元数量和篇幅分配实现；在提纲里复述「60%/40%」不算实现。
8. **标题也是人话**。「第 8 章｜借条上是师父的签名」比「第八章：核心矛盾的深化与推进」有用。目录本身应该能当故事梗概或内容提要读。

## 一条大纲长什么样（检查用，不是填空表）

```text
[单元号]｜[谁] 在 [具体地点 / 对着哪份材料] 想 [具体目的]，
[谁或什么] 拦了一下（[具体阻碍]），他/她 [做了什么动作]，
结果 [具体变化：多了什么、少了什么、知道了什么、失去了什么]。
下一单元非写不可，因为 [还没解决的那个具体问题]。

附注：H-03 推进｜口径：2026 年一季度出货量｜预算：约 1800 字
```

顺序可以打乱，不必每行套；写成一整段更自然。这个模板只用来**事后检查**：有没有人、有没有动作、有没有具体阻碍、有没有变化。真写成五段填空，就又回到机器腔了。

## 「具体」在不同文体里指什么

| 文体 | 大纲里该出现的具体东西 |
| --- | --- |
| 网文 / 小说 | 谁在哪、拿到什么、谁拦着、说了哪句话、关系怎么变、下一章追着谁去 |
| 深度报道 / 特稿 | 去查谁、看哪份文件、谁否认了、原话怎么讲、还差哪个信源没核实 |
| 报告 / 书稿 | 先摆哪组数字、用哪个反例检验论点、结论被限到什么范围、口径是哪一年 |
| 评论 / 专栏 | 先亮哪个判断、让谁提出最强反驳、拿哪件事把反驳挡回去 |
| 科普 / 教程 | 读者照着做哪一步、屏幕上会出现什么、哪一步最容易失败、失败时看见什么 |
| 论文 | 用哪份数据跑哪个检验、预期图表画什么、如果结果相反说明什么 |
| 技术文档 / SOP | 用户在什么版本和权限下点哪里、得到什么输出、报错码是什么 |
| 提案 / 演讲稿 | 听众先听到哪个具体损失、给他哪一个动作、结尾回到开头的哪句话 |
| 制度文本 | 谁向谁提交、几天内、依据哪一条、逾期怎么办 |

## 写完读一遍

- 念给没看过材料的人听，他能不能复述出「谁干了什么」？
- 每条里有没有至少一个具体名词和一个看得见的动作？
- 有没有「功能 / 作用 / 深化 / 推进 / 强化 / 赋能 / 闭环 / 维度 / 层面 / 相关 / 若干 / 一定程度」？
- 有没有把还没写的事写成已经发生？
- 台账 ID、比例、字数预算是不是都退到附注里了？
- 标题能不能单独当一句人话读？

## 例外与边界

- 机器可读字段（hook ID、schema 字段、字数预算、口径版本）该留就留，放到附注或末尾，不占正文。
- 制度、SOP、API 文档可以保留层级目录，但每一级下面的说明仍要写具体动作与结果，不能只写「本章规定了相关管理要求」。
- **审稿意见、修订说明、契约本身不是大纲**，它们本来就要说功能与标准，不受「不写功能」限制；但引述原文时照样要具体。
- 大纲说人话不等于大纲口语化。别撒语气词、别写段子、别把「她大概可能也许会去」当成谨慎——具体和含糊是两回事。
- 大纲里的事实仍受事实基座约束：不编造数据、年份、文献与法规；不确定的地方在附注里标「待核对」，不要用模糊修辞糊过去。

配套的 `scripts/check_outline.py` 会把上面这些症状挑出来，**它是提示器不是裁判**：命中只说明这句值得重写，不命中也不保证大纲就写得好。
